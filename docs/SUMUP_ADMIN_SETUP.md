# SumUp: настройка из админки Trosheen

## Где настраивать

Админка → Настройки → **SumUp · Оплата на сайте** (`/admin/settings#sumup`).
Это интернет-оплата через Hosted Checkout, не настройка физического терминала.
API key и Merchant code после развёртывания вводятся здесь, без изменения .env и
без перезапуска приложения. Код не включает оплату сам и не выполняет реальных
платежей при проверке или сохранении.

1. В SumUp Dashboard выберите нужный merchant, откройте Settings → For Developers →
   API Keys и создайте **секретный** API key. Скопируйте Merchant code того же аккаунта.
   Public key / affiliate key / OAuth Client ID / Client Secret для этого сценария
   собственного магазина не нужны.
2. Введите API key, Merchant code, публичный HTTPS-домен (например,
   `https://trosheen.shop`) и начало описания платежа. Валюта фиксирована: EUR,
   поскольку каталог и существующий checkout магазина работают в евро.
3. «Проверить без сохранения» читает merchant через API; проверяются принадлежность
   merchant, EUR и флаг Sandbox. Изменений в БД и списания нет.
4. «Проверить и сохранить» сохраняет проверенные ключи в зашифрованном виде.
   **Сохранение отключает новые платежи**, даже при редактировании описания/домена.
   Пустое поле API key сохраняет уже настроенный ключ; оно не удаляет его.
5. Для рабочего аккаунта отдельно нажмите «Включить оплату покупателей» и подтвердите
   merchant и домен. Сервер повторно проверит аккаунт. Sandbox включить нельзя.
   «Выключить оплату» работает без обращения к SumUp, даже во время его недоступности.

Проверка merchant не подтверждает завершение онбординга/активации онлайн-платежей,
получение денег или доступность webhook. Перед публичным запуском пройдите Sandbox
и отдельно контролируемый небольшой настоящий заказ своими силами.

## Проверка в Sandbox

Создайте sandbox merchant в SumUp Dashboard и сохраните его собственные ключи/code.
Раздел «Проверочная оплата в Sandbox» создаёт отдельную тестовую страницу на 1 EUR
после подтверждения. Само создание страницы не оплачивает её. Пройдите оплату
тестовой картой из актуальной документации SumUp, затем нажмите «Проверить результат».
В магазине не создаётся заказ, не меняются остатки, не запускается производство и
не отправляется уведомление о покупке в Telegram. После проверки сохраните рабочие
ключи и отдельно включите реальные платежи.

Режим определяется по `GET /v1/merchants/{merchant_code}` (поле `sandbox`), а не
по произвольному переключателю «тест/бой». Неизвестный режим не допускает включения.
Sandbox-страница открывается в отдельной вкладке. Результат можно обновить в исходной
вкладке настроек. После перезагрузки страницы локальная карточка теста не сохраняется;
сам тестовый checkout остаётся записанным в БД и в кабинете SumUp.

## Callback, Cloudflare и отключение

Адреса выводятся в настройках, есть кнопки копирования. Они производятся из сохранённого
HTTPS-домена, не из входящего Host header:

- backend callback: `/api/checkout/webhook` (`return_url` в запросе SumUp);
- возврат покупателя: `/order-confirmation` с order_id и подписанным токеном;
- для отдельного Sandbox-теста: возврат на `/admin/settings#sumup`.

Callback передаётся автоматически при создании каждого checkout. Дополнительной
ручной регистрации webhook или нового порта Raspberry Pi не требуется. Существующий
домен/Cloudflare Tunnel должен пропускать POST на callback без Cloudflare Access,
логина, CSRF или интерактивной проверки браузера. Проверка из админки не проверяет
доступность этого входящего маршрута. Не удаляйте старый домен callback, пока есть
выданные через него незавершённые оплаты.

Выключение блокирует новые checkout-запросы. Уже начатый запрос/выданная страница
может завершиться; её результат продолжает проверяться. Корзина сохраняется, покупатель
видит сообщение о недоступной оплате на EN/LV/RU/PL/UK. Проверка доступности обновляется
периодически, но окончательное разрешение всегда принимает сервер.

## Безопасность и совместимость

- Ключ AES-256-GCM защищён merchant-specific AAD. Шифрующий секрет:
  `PAYMENTS_ENCRYPTION_SECRET`, иначе существующий `SESSION_SECRET`, минимум 32 символа.
  Секрет сервера не задаётся из браузера. Он должен оставаться постоянным и входить в
  резервную копию конфигурации. Не меняйте выбор/значение секрета после сохранения ключей
  без переноса; существующие зашифрованные записи станут недоступны.
- API key не возвращается в GET/PUT/test-ответах и не помещается в public settings,
  localStorage, URL или журналы. DTO проверенного merchant содержит только безопасные
  поля. Транспорт не публикует сырые тела/ошибки SumUp.
- Все настройки защищены adminAuthMiddleware и существующей глобальной CSRF-защитой.
  Записи повторно проверяют роль администратора внутри транзакции и ожидаемую версию.
  Одновременные изменения не перетирают друг друга молча.
- До первой сохранённой конфигурации сохраняется совместимость с SUMUP_API_KEY и
  SUMUP_MERCHANT_CODE окружения. На первом admin-save старый env-ключ архивируется
  зашифрованным для проверки дорефакторинговых заказов. Не удаляйте старые env-данные
  до этого переноса, если остались старые оплаты без binding.
- Новые checkout привязаны к исходным merchant/credential/amount/currency/reference.
  Изменение выбранного merchant не перенаправляет проверку старого заказа на другой
  аккаунт. При ротации используется последний проверенный ключ того же merchant.
  Отозванный в SumUp ключ всё равно потребует замены действительным; магического
  обхода отзыва доступа нет.
- Ревизии ключей сохраняются зашифрованными для ранее выданных оплат. Автоматическое
  удаление истории ключей не добавлено; в будущем очистку следует связывать с
  окончательной сверкой всех затронутых платежей.
- После callback сервер самостоятельно получает checkout из SumUp и сравнивает
  точные ID, reference, merchant, EUR и сумму. Sandbox callbacks не выполняют заказ.
  Сохраняются транзакционные склад/Telegram outbox и защита от повторного callback.
- При неоднозначном сетевом сбое создания оплаты локальный pending-заказ больше не
  удаляется: SumUp мог принять запрос. Автоматического повторного списания/создания нет.
  Сверьте такой заказ в SumUp до ручного повторного платежа. Это не полная система
  автоматической сверки потерянных удалённых ответов.

## Миграция и развёртывание

Добавлена `migrations/0017_sumup_admin_setup.sql`:
`sumup_credentials`, `sumup_payment_config`, `sumup_checkout_bindings`.
Применять SQL-миграции до запуска новой версии (обычный ручной deploy.sh / npm run migrate),
не db:push. Сделайте резервную копию PostgreSQL и постоянного серверного секрета.
Новых runtime-зависимостей или автоматического deployment нет. Существующий
SESSION_SECRET обычно уже задан; API key и merchant code после обновления настраиваются
только из админки. Отдельный PAYMENTS_ENCRYPTION_SECRET необязателен; при его использовании
он должен быть передан именно в окружение приложения/контейнера, не только записан в файл.

## Проверка реализации

```sh
node --test tests/sumup-admin.test.cjs
npm run build
```

В среде реализации выполнены 42 целевых теста без ошибок/пропусков. Они проверяют
шифрование, отсутствие секретов в ошибках/DTO, конфигурацию/версии/права, env-перенос,
ротацию merchant/key, disabled/Sandbox, точность платежей, rollback, route handlers,
повторные callbacks и интеграцию Telegram outbox. Строгая проверка TypeScript прошла
для пяти новых core/shared модулей; 13 изменённых/новых TS/TSX проверены на синтаксис.
SQL и HTTP в тестах заменены адаптерами. Реальный PostgreSQL, браузерная отрисовка,
полная сборка сайта и реальные SumUp/Telegram/Raspberry Pi здесь не запускались.

После развёртывания отдельно проверить: миграции, сохранение/перезапуск без потери
ключа, отклонение неверного merchant, Sandbox success/failure, pause/resume, полный
реальный заказ → подтверждение оплаты → единственное уведомление Telegram, недоступность
callback и корректную сверку при ротации ключа с незавершённой оплатой.
