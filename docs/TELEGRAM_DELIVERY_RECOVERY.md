# Trosheen Workshop — доставка уведомлений и восстановление

## Администратору

Настройки → Telegram · Trosheen Workshop → «4. Доставка уведомлений».
Журнал показывает номер заказа, сотрудника, число попыток обработки, время следующей
попытки и понятное объяснение ошибки. Доступны фильтры, страницы по 20 уведомлений,
обновление раз в 10 секунд и ручное обновление. Все даты отображаются для Europe/Riga.

«Доставлено» означает: Telegram принял сообщение и сервер сохранил подтверждение.
Это не подтверждение прочтения отцом и не статус оплаты или изготовления.

Временные ошибки повторяются автоматически с увеличением задержки до одного часа.
После 12 последовательных попыток без успеха запись требует вмешательства.
Ошибки 400/401/403/404 требуют проверки формата, токена или доступа к чату, а не
бесконечных повторов. Telegram 429 обрабатывается отдельно: retry_after сохраняется
в PostgreSQL как пауза исходящей очереди. Пауза переживает перезапуск; её не сокращают
ручной повтор, выключение/включение или обновление токена того же бота.

Для записи «Нужна помощь» исправьте причину, затем нажмите «Повторить отправку
уведомления» и подтвердите конкретного получателя и номер заказа. Сообщение только
возвращается в очередь — это не обещание немедленной доставки. Общий счётчик попыток
сохраняется; новая серия автоматических попыток начинается с нуля. В БД сохраняются
время и ID администратора последнего ручного повтора, не полная история повторов.

Успешные, остановленные, уже обрабатываемые уведомления и сообщения для отключённого
сотрудника вручную не переотправляются. Отменённый/неоплаченный заказ не проходит
повторную отправку. Такие записи останавливаются, а не крутятся в очереди бесконечно.
Выключение бота оставляет подходящие уведомления в очереди. Отключённые сотрудники
не получают сообщения, пока их доступ не включён. Заказы без настроенных получателей
не получают новых адресатов задним числом: это прежнее поведение постановки в очередь.

## Разработчику

- `workshopTransport.ts`: typed TelegramRequestError, HTTP timeout, code/retry_after,
  безопасные сообщения без сырых тел провайдера, URL токена и данных покупателя.
- `workshopDelivery.ts`: отдельный worker, PostgreSQL advisory lock между экземплярами,
  SKIP LOCKED, токен аренды на каждой попытке и проверка токена при записи результата.
- Перед отправкой повторно проверяются текущий бот/токен, включённый сотрудник,
  статус заказа и наличие платёжной ссылки. Уже начатый HTTP-запрос отозвать нельзя;
  это не обещание атомарности между отзывом доступа и сетью.
- Запись успешного ответа Telegram находится вне обработчика ошибок отправки.
  Ошибка сохранения квитанции не подменяется «известным отказом Telegram».
- В публичный DTO журнала не попадают chat_id, токен, зашифрованный токен, адрес,
  телефон или email клиента. Даже старые сырые last_error заменяются безопасным текстом.
- `GET /api/admin/telegram-workshop/deliveries?page=0&filter=attention`.
- `POST /api/admin/telegram-workshop/deliveries/:id/retry`, тело `{ "confirm": true }`.
  Действует существующий admin middleware и CSRF; роль администратора проверяется
  снова внутри транзакции. Автор повтора берётся из сессии, не из тела запроса.
- Платёжные, складские и производственные таблицы этот сервис не изменяет.

Доставка не exactly-once. При потере ответа Telegram или сбое БД после успешной
отправки повтор после истечения аренды может дать дубль сообщения. Сверяйте номер
заказа; платежи/производственные действия от дублирования уведомления не повторяются.
Журнал не удаляется автоматически. Замена бота/удаление получателя сохраняют прежнее
каскадное удаление их очереди; эта доработка не меняет политику хранения.

## Развёртывание и проверка

Добавочная миграция: `migrations/0016_workshop_delivery_recovery.sql`. Применить до
запуска нового приложения через существующий ручной deploy.sh / `npm run migrate`.
Сначала резервная копия БД. Запускать SQL-файлы, не db:push: новые таблицы Telegram
по-прежнему ведутся SQL-миграциями. Никаких новых runtime-зависимостей, webhook,
входящих портов или автоматического развёртывания не добавлено.

```sh
node --test tests/workshop-production.test.cjs tests/workshop-delivery.test.cjs
npm run build
```

В среде разработки выполнены 67 целевых тестов (38 доставки, 29 производства),
без ошибок и пропусков. Новые транспорт, delivery-сервис и общий DTO прошли строгую
проверку TypeScript; изменённые TS/TSX проверены на синтаксис/transpilation.
SQL-тесты используют адаптер базы, а не реальный PostgreSQL. Полная сборка сайта,
браузерная проверка интерфейса, применение миграций к PostgreSQL и реальные
Telegram/SumUp/Raspberry Pi при этой доработке не выполнялись.

На тестовом сервере после миграции проверить: успешную оплату → одно уведомление;
повтор webhook не добавляет дубль; сбой сети → автоматический повтор; заблокированный
бот → понятную ошибку и подтверждённый ручной повтор после разблокировки; отключение
сотрудника; отмену заказа до доставки; сохранение flood-паузы после рестарта;
одновременные workers и одновременные ручные повторы из двух админских окон.
Полная проверка PostgreSQL-конкуренции остаётся обязательной перед production.
