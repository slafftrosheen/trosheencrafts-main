# Trosheen Workshop — изготовление заказа

## Что добавлено

В карточке Telegram появились «Изготовление и готовность» и история действий. Путь:
«Взять в работу» → «Отметить: изготовлено» → «Готово к отправке».
После изготовления/упаковки можно явно вернуть заказ в работу для исправлений.
Каждое изменение подтверждается отдельной кнопкой. Старое подтверждение не меняет
новую версию заказа. В истории сохраняются время, сотрудник, источник (Telegram или
админка) и переход. Время отображается для Europe/Riga.

Тот же блок доступен в админке: Заказы → развернуть заказ → Изготовление.
Открытый блок обновляется каждые 10 секунд; в Telegram нажмите «Обновить состояние»
или откройте заказ заново. Старые сообщения во всех чатах не редактируются автоматически.
История выдаётся по 8 записей, список активных заказов Telegram — по 8 заказов.

## Границы и безопасность

Это отдельный производственный статус, не подтверждение оплаты. Изменения разрешены
только для `orders.status = processing` с сохранённой платёжной ссылкой. Для pending,
payment_review, cancelled, shipped, delivered действия закрыты. Оплата, запасы,
возвраты и доставка этим сервисом не меняются. «Готово к отправке» не уведомляет
покупателя и не переводит заказ в shipped. Разрешение проблем payment_review остаётся
отдельной операцией существующего платёжного/складского процесса.

Проверка сотрудника и включённого бота повторяется в транзакции записи. Для админки
повторно проверяется текущая роль пользователя. Сервис блокирует родительский заказ,
проверяет ожидаемую версию и сохраняет состояние вместе с историей в одной транзакции.
Имя в истории — снимок на момент действия; удаление получателя или замена бота историю
не стирают. Удаление самого заказа удаляет связанную историю по внешнему ключу.

Новые таблицы ведутся SQL-миграциями, как существующие таблицы Telegram. Не запускайте
`db:push` для применения этой функции. Старые заказы не получают выдуманную историю:
без производственной записи показывается «Ожидает изготовления», а отправленные
заказы остаются только для просмотра.

## Развёртывание

Изменения в main не являются развёртыванием. Выполняйте штатный ручной deploy.sh,
который собирает образ и применяет миграции до запуска нового приложения. Миграция:
`migrations/0015_workshop_production.sql` — таблицы `order_production` и
`order_production_events`. Она добавочная, не меняет существующие заказы.

Для ручного запуска мигратора с настроенным DATABASE_URL:

```sh
npm run migrate
```

Бот продолжает исходящее HTTPS-подключение к Telegram. Публичный Telegram webhook,
Mini App, входящие порты и новые runtime-зависимости не добавлялись.

## Проверки

С установленными devDependencies репозитория:

```sh
node --test tests/workshop-production.test.cjs
npx tsc --noEmit --strict --target ES2022 --module commonjs shared/workshopProduction.ts
npm run build
```

В рабочей среде автора изменений выполнены 29 тестов node:test, включая правила,
версионные конфликты, проверки доступа, rollback при ошибке аудита, подтверждения,
экранирование HTML, пагинацию истории и восстановление polling после отказа connect.
Тест SQL-сервиса использует тестовый адаптер pg, не настоящий PostgreSQL.
Синтаксис изменённых TS/TSX файлов проверен через TypeScript transpileModule; отдельно
проверены строгие типы общего модуля. Это не полная сборка или проверка типов приложения.
Полная сборка, применение SQL к PostgreSQL, реальный Telegram/SumUp и Raspberry Pi
при написании документа не запускались.

## Приёмка на сервере

1. Применить миграции, собрать и запустить приложение; убедиться, что старые настройки
   бота и получатели сохранились. Приглашение и тестовое сообщение должны работать.
2. Для оплаченного тестового заказа открыть изготовление в Telegram. Нажать первый
   шаг и отменить: статус/история не меняются. Подтвердить: одна запись в истории,
   админка видит состояние в течение следующего обновления.
3. Открыть одно подтверждение на двух устройствах. Подтвердить на одном, затем на другом:
   второе действие сообщает об устаревшем состоянии, не создаёт вторую запись.
4. Пройти изготовление и упаковку, затем вернуть в работу. Проверить историю в обоих
   интерфейсах. Статус платежа и остатки не должны измениться.
5. Отключить получателя между открытием подтверждения и нажатием: изменение запрещено.
   Проверить аналогично отменённый, отправленный и payment_review заказы.
6. Проверить очередь из более 8 заказов и историю из более 8 событий: следующие страницы
   доступны. Проверить клавиатуру/фокус в диалоге админки и большие настройки шрифта Telegram.
7. Кратковременно остановить PostgreSQL, восстановить его и проверить, что polling
   возобновился без ручного перезапуска приложения.
